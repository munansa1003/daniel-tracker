# Body Plan — 인바디 체성분 자동 수신 확장 구현 요청 (신규 세션용)

> **새 세션 안내**: 이 세션은 운동 자동 수신(#75~#87)을 구현한 세션과 다른 세션이다.
> 맥락은 전부 이 문서와 레포 안에 있다 — Phase 0의 필독 파일부터 읽고 시작하라.

## 0. 배경 — 무엇을 왜 만드나

애플워치 운동 자동 수신은 완료·실전 검증됐다(HAE Basic 단축어 → /api/health-import → KV 사서함 → 앱 병합). 이번엔 같은 파이프라인을 **체성분(인바디)으로 확장**한다.

현재 워크플로우: 인바디다이얼 H20으로 아침 공복 측정 → InBody 앱 확인 → Body Plan에 체중·골격근·체지방률·점수 4개를 손으로 입력. InBody 앱은 애플 건강에 **체중·체지방률·제지방체중**을 쓰고 있음을 실기기로 확인했다(골격근량·인바디점수는 HealthKit에 항목 자체가 없어 어떤 방법으로도 자동화 불가).

**목표 워크플로우:**

```
H20 측정 → InBody 앱 열람(=건강 동기화) → 앱 닫기
  → 단축어 자동화: HAE '지표 내보내기'(체중·체지방률·체질량) → POST
  → 검문소 → KV 사서함 → 앱 열 때 "완성 대기 초안"으로 착지
  → 사용자는 골격근·점수 2개만 입력 → 확정(잠금)
```

타이핑 4개 → 2개. 이 설계는 3라운드 교차 검증을 거쳤고, 아래 규칙들은 그 결과다 — **임의 완화 금지.**

## 1. 수신 스펙

### 1.1 입력 (HAE '건강 지표 내보내기' JSON)

문서 기준 형태: `{ data: { metrics: [ { name, units, data: [ { date, qty } ] } ] } }`
날짜는 운동과 같은 `yyyy-MM-dd HH:mm:ss ±0900`류 — **기존 운동 파서의 날짜 처리를 재사용**하라.

지표 매칭은 **이름 키워드 기반(관대한 파서)**:
- weight/체중 → weight 후보
- fat/체지방 → fatPct 후보
- lean/체질량/제지방 → lbm(보조 저장)
- 그 외(bmi·키·허리둘레 포함) → 무시 + **수신 로그에 원본 name 기록** (추후 별칭 확장용 — 운동의 "대상 외 제외" 패턴 재사용)

정확한 필드명·형은 첫 실전송에서 확정한다 — 그래서 **수신 로그가 스펙의 일부**다(1.4).

### 1.2 검문 규칙 (전부 하드 요구)

| # | 규칙 | 내용 |
|---|---|---|
| B1 | **아침 창 가드** | 측정 시각이 00:00~12:00(로컬) 밖이면 초안 갱신 대상에서 제외 + 로그. "아침 공복 1회 고정"이라는 검증된 측정 규칙의 코드화 — 저녁 비공복 측정이 아침 값을 덮는 사고 방지 |
| B2 | **day-keyed 최신 갱신** | 운동의 insert-only와 **다른 도메인 규칙**. 하루 1초안, 같은 날(아침 창 내) 더 최신 타임스탬프가 오면 초안 값 갱신. 근거: 실측 패턴(8/5 3회 재측정 08:24→09:19→09:20, 마지막이 정답 — 7/30 교차 검증 완료) |
| B3 | **다중 샘플 처리** | 같은 날 샘플 여러 건이면 **최신 타임스탬프 채택**. 하루 1건(집계 평균)으로 와도 동작하되 수신 로그에 "오늘 샘플 수"를 남겨 집계 형태를 판별 가능하게 |
| B4 | **소수형 의심 방어** | 체지방률 값이 0 초과 1 이하면(예: 0.187) "소수형 의심"으로 거부+로그. 유효 범위 3~60. HealthKit 내부 표현(0~1)이 그대로 올 가능성 대비 — 첫 실전송에서 형 확정 후 필요 시 ×100 변환을 별칭처럼 추가 |
| B5 | **단위 방어** | weight/lbm: kg만 수용, lb는 변환(×0.4536) 후 수용, 그 외 거부+로그. 범위: weight 40~150, lbm 30~80 |
| B6 | **소스 필터(옵션)** | 페이로드에 소스 정보가 있으면 InBody 소스만 수용하는 필터 구현, 없으면 로그로 소스 관찰만 (현재 쓰기 소스는 InBody뿐 — 미래 오염 대비) |
| B7 | **컷오버** | 시작일 이전 측정 거부 (env `IMPORT_BODY_CUTOVER_DATE`). 잠금(1.3)이 구조적으로 이중 계상을 막지만 안전벨트로 유지 |
| B8 | **부분 수신 허용** | weight만 오고 fatPct가 없어도 초안 성립 — 필드별 독립(누락 필드는 비움) |
| B9 | **로그 위생** | 본문 전문 로그 금지, 요약(건수·소스·오늘 샘플 수·미매칭 name)만 |

인증·토큰·503 규칙·본문 크기 가드는 기존 검문소와 동일 (IMPORT_TOKEN·IMPORT_UID 재사용).

### 1.3 병합·잠금 (앱 계층 — 여기가 핵심)

- 자동 수신분은 정식 body 레코드가 아니라 **"완성 대기 초안"**으로 착지: 체중·체지방률(+lbm 보조) 미리 채움, 골격근·점수 입력란 비움
- **불변 조건: muscle 미입력 상태가 골격근 통계(추이·MA7·기간 요약)에 0으로 오염되면 절대 안 됨** — 구현 방식은 3안에서 (2절)
- **잠금**: 사용자가 골격근(+점수)을 입력해 저장하는 순간 그날은 확정. 이후 도착하는 초안·갱신은 **병합 계층에서 폐기**(서버는 확정 여부를 모르므로 잠금 집행 지점은 병합 계층이다). 수동으로 먼저 입력한 날 = 같은 잠금으로 자동분 폐기
- **사서함 ack 의미론 불변**: 초안을 KV에 보류하는 설계 금지 — pull 즉시 앱 저장소에 착지시키고 ack(HDEL)
- **LBM 오타 가드**: 골격근 입력 시 `입력값 ÷ 당일 lbm`이 **0.53~0.61 밖이면 경고**(차단 아님). 근거: 297일 실측 SMM/LBM ≈ 0.56~0.58로 매우 안정 — 34.7을 43.7로 치면 0.72로 튀어 즉시 검출. lbm이 없는 날은 가드 생략
- **골격근 자동 기입 절대 금지**: lbm×비율 추정으로 muscle을 채우는 코드 금지 — 추적 지표 오염. 가드는 경고 전용

### 1.4 관측성 — 첫 실전송 확인 3종의 판별 창구

수신 로그(기존 자동 가져오기 카드 확장)에서 다음이 보여야 한다: ⑴ 매칭된 지표명 원본 ⑵ 체지방률 수신값 형(18.7 vs 0.187 → B4 발동 여부) ⑶ 오늘 샘플 수(개별 vs 집계). 이 셋은 문서로 확정 불가능해 운영 첫 주에 판별하는 항목이며, 로그만으로 판별되도록 설계하라.

### 1.5 UI 최소 요구

- 초안 상태 표시: "체중·체지방률 자동 수신됨 — 골격근·점수 입력하면 확정" + ⌚(또는 별도) 배지
- 확정 후에도 전체 편집·삭제 가능 (잠금은 자동 갱신 차단이지 수동 편집 차단이 아님)
- LBM 경고 노출 위치는 입력 폼 인라인

## 2. Phase 1 — 구현안 3가지 (필수, 승인 대기)

서로 의미 있게 다른 3안. 최소 차별화 축:

- **엔드포인트**: 기존 `/api/health-import`에 페이로드 자동 판별(metrics vs workouts) vs kind 파라미터 분기 vs `/api/body-import` 신설
- **초안 스키마**: day 문서에 `pendingBody` 필드 vs body 레코드 muscle-null 허용(+모든 통계의 null 스킵) vs 별도 draft 저장
- **사서함**: 기존 inbox에 kind 구분 필드 vs 별도 inbox 키

비교표 필수 항목: 변경 규모 · **운동 파이프라인 격리성**(체성분 오류가 운동 수신을 인질로 잡지 않는가) · 통계/공유 링크 파급 · 롤백 용이성 · 확장성(허리둘레 등 지표 추가 시). 추천 1개 + 이유 명시.

## 3. Phase 3 — 계약 테스트 (골든셋 등록, 최소 15종)

| # | 입력/상황 | 기대 |
|---|---|---|
| 1 | 아침 weight 73.6 + fatPct 18.7 + lbm 60.5 | 초안 생성, 3값 채움 |
| 2 | 같은 날 개별 3샘플 73.8(08:24)→73.7(09:19)→73.6(09:20) | 최신 73.6 채택 (8/5 실증 재현) |
| 3 | 하루 1건(집계 평균) 형태 | 정상 처리 + 로그에 샘플 수 1 |
| 4 | fatPct 0.187 | 거부 + "소수형 의심" 로그 |
| 5 | weight units lb (예: 162.3) | kg 변환 73.6 수용 |
| 6 | 21:00 측정 샘플 | 아침 창 밖 — 초안 갱신 제외 + 로그 |
| 7 | 골격근 입력 확정 후 늦은 초안 도착 | 병합 계층 폐기, 값 불변 |
| 8 | 수동 선입력한 날 초안 도착 | 폐기 (잠금 동일 적용) |
| 9 | muscle 미입력 초안 존재 상태 | 골격근 추이·MA7·기간 요약에 0 미출현 |
| 10 | muscle 43.7 입력 (lbm 60.5) | 비율 0.72 → 경고 표시, 저장은 허용 |
| 11 | 컷오버 이전 날짜 | 거부 |
| 12 | 지표명 "waist_circumference" | 무시 + 로그에 name 기록 |
| 13 | analysisExport(공유 링크) | 초안 미확정 날의 노출 규칙이 정의대로 (초안임이 표시되거나 제외 — Phase 1에서 규칙 확정) |
| 14 | 운동 페이로드 회귀 | 기존 운동 수신 경로 전 케이스 무손상 (기존 골든셋 전체 통과) |
| 15 | 앱닫힘 트리거 + 21:30 백업 동시 도착 | 멱등 — 최종 상태 동일 |

추가: curl 실전 시뮬레이션(프리뷰 URL, 정상/소수형/창밖/토큰오류 4케이스) 기록 첨부, 훅·CI 녹색.

## 4. Phase 5 — docs/inbody-setup.md (산출물)

hae-setup.md와 같은 구조로: 최종 아키텍처 도식 / 단축어 레시피(**별도 단축어 "Body Plan 체성분 전송"** — 실패 격리 원칙: 운동 단축어에 블록 삽입 금지) — HAE '건강 지표 일괄 내보내기' 블록 설정(지표: 체중·체지방률·체질량 3종만 · 기간 오늘 · **집계 없음/최소 단위** · JSON · 실행 시 보기 끔) + POST 블록 / **자동화 C**: "InBody 앱이 닫힐 때 → 즉시 실행" (순서 보장 트리거 — 시간 트리거는 앱 동기화 전 헛방 위험) / 기존 21:30 백업 자동화에 이 단축어를 **추가 동작**으로 등록 / 운영 수칙(인바디 앱을 안 연 날은 자동화가 침묵하므로 수동 입력이 폴백, "체질량=제지방" 확인법: 값이 건강 앱 제지방과 일치하는지) / 문제 해결 표(첫 실전송 확인 3종 포함) / 환경변수 안내(IMPORT_BODY_CUTOVER_DATE 추가).
