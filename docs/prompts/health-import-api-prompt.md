# Body Plan — 애플워치 운동 자동 수신 API 구현 요청 (단축어 연동 1단계)

## 0. 배경 — 무엇을 왜 만드나

지금까지 워크플로우: 워치로 운동 → 아이폰 피트니스의 칼로리를 눈으로 보고 Body Plan에 손으로 입력. 이걸 자동화한다.

**확정된 아키텍처 (3차 교차 검증 완료):**

```
애플워치 (운동 종료)
 → 아이폰 건강 앱 (HealthKit)
 → iOS 단축어 (운동종료 트리거 + 저녁 백업 + 원탭 버튼, 총 3중)
 → [이번에 만드는 것] Body Plan 수신 API (검문소)
 → Firebase 저장 → 유효목표(1,536 + 운동×50%) 자동 반영
```

이번 작업 범위는 **수신 API(검문소) + 최소 UI + 단축어 조립 가이드 문서**다. 단축어 자체는 내가 폰에서 조립한다 — 너는 그 조립 설명서를 산출물로 만들어라.

핵심 설계 원칙 (검증에서 확정, 변경 불가):
- **insert-only** — 같은 운동이 여러 번 도착하는 건 기본 동작(3중 자동화). 한 번 들어온 운동은 무시, 절대 갱신하지 않는다. 사용자가 수정한 기록을 재전송이 덮어쓰는 사고를 원천 차단.
- **유산소만 자동** — 워치는 근력을 "기능성 근력 훈련" 한 덩어리로만 알아서, 근력을 자동화하면 상체/하체 부위 통계가 붕괴한다. 근력은 수동 유지.
- **컷오버** — 시작일 이전 데이터는 거부. 과거 297일 수동 기록과의 이중 계상 차단.
- **단일 출처** — 유효목표 계산은 기존 중앙 함수를 재사용. 수신 경로에서 목표를 재계산하는 사본 코드 금지.

## 진행 방식 (순서 엄수)

- **Phase 0** — 현황 파악: 운동 기록의 현재 데이터 스키마, 유효목표 계산 단일 출처 함수의 위치, 휴식일 프리셋(dayType)의 자동 복귀 로직 위치를 코드에서 확인해 보고
- **Phase 1** — 구현안 3가지 제안 (비교표 + 추천 1개) — **여기서 멈추고 내 승인 대기**
- **Phase 2** — 승인된 안으로 구현
- **Phase 3** — 검증: 계약 테스트 10종 + 기존 골든셋 전체 회귀 + curl 실전 시뮬레이션
- **Phase 4** — PR + Vercel 프리뷰 → 내 확인·승인 후 main 머지
- **Phase 5** — 단축어 조립 가이드에 실제 배포 URL 반영해 최종화

**Phase 1 승인 전에는 코드를 수정하지 말 것.**

## 1. 수신 API 스펙

### 1.1 엔드포인트

- `POST /api/health-import` (경로명은 제안 가능)
- 인증: 헤더 `X-Import-Token: <비밀값>` — Vercel 환경변수로 관리. **토큰 환경변수가 미설정이면 엔드포인트는 503으로 비활성** (실수 배포 방지)
- 참고: AI 공유 링크 때 확인된 "쿼리스트링 유실" 문제는 Claude 웹 리더 한정이고 단축어의 POST와는 무관하다. 그래도 인증은 표준대로 헤더로 간다.

### 1.2 요청 본문 (우리가 정의하는 스키마 — 단축어가 이대로 조립)

```json
{
  "source": "workout-end | evening-backup | manual-tap",
  "sentAt": "2026-08-06T19:00:12+09:00",
  "workouts": [
    {
      "type": "실외 달리기",
      "start": "2026-08-06T18:20:00+09:00",
      "end": "2026-08-06T18:50:00+09:00",
      "durationMin": 30,
      "kcal": 446,
      "device": "Apple Watch"
    }
  ]
}
```

- 날짜는 **오프셋 포함 ISO 8601 필수**. 위반 시 400 + 에러 메시지에 "ISO 8601 필요"를 명시 (단축어 디버깅용)
- `type`은 단축어가 주는 문자열 그대로 받는다 — 한국어/영어 어느 쪽이 올지 기기 언어에 달렸으므로 서버 매핑 테이블이 흡수한다 (1.4)
- 본문 크기 100KB 초과 시 400 (정상 페이로드는 수 KB)

### 1.3 응답 — 단축어가 알림으로 띄울 수 있게

```json
{
  "accepted": 2, "ignored": 1, "filtered": 1, "rejected": 0,
  "message": "2건 추가 · 중복 1 무시 · 근력 1 제외"
}
```

- `message`는 한국어 한 줄 요약 — 단축어가 이 값을 그대로 알림으로 표시한다
- 상태코드: 200 정상 처리 / 400 스키마·검증 실패 / 401 토큰 불일치 / 405 POST 외 / 503 토큰 미설정

### 1.4 검문소 규칙 8종 (지뢰 해체 — 전부 하드 요구사항)

| # | 규칙 | 구현 |
|---|---|---|
| 1 | **스키마 엄격 검증** | 필수 필드 누락·타입 오류는 400. 부분 성공 허용(운동 단위로 판정) |
| 2 | **값 상식 검사** | kcal은 정수 반올림 저장, 1~2,000 범위 밖이면 rejected (kJ 오염·이상치 차단). durationMin 1~600 |
| 3 | **유산소 화이트리스트** | 허용 유형만 저장, 나머지는 `filtered`. 매핑 테이블은 **한 파일 단일 출처**, 한국어/영어 병기: 달리기·Running·Outdoor Run / 사이클링·Cycling·Indoor Cycling / 걷기·Walking / 축구·Soccer·Football / 계단 오르기·Stair Climbing / 하이킹·Hiking / 수영·Swimming. 근력 계열(기능성 근력 훈련·Functional/Traditional Strength Training)은 명시적으로 filtered. 미등록 유형도 filtered + 로그에 유형명 기록(추후 테이블 확장용) |
| 4 | **insert-only 중복 차단** | dedup 키 = `정규화(type) + start + end` (kcal은 키에서 제외 — 워치에서 칼로리를 나중에 수정해도 재유입 안 되게). 기존 존재 시 `ignored`, **update 절대 금지** |
| 5 | **동시 도착 원자성** | 운동종료 트리거와 백업이 겹치면 같은 운동이 동시에 2요청으로 올 수 있다. race에도 1건만 저장되는 원자적 방법 필수 — *문서 ID 자체를 dedup 해시로 쓰고 create-only 쓰기를 하면 원자성이 공짜로 확보되는 안*을 3안 중 최소 1개에 포함하라 |
| 6 | **컷오버** | 환경변수 `IMPORT_CUTOVER_DATE` 이전에 시작된 운동은 rejected. 과거 백필 차단 |
| 7 | **날짜 귀속** | 기록일 = **시작 시각의 로컬 날짜** (오프셋 기준). 자정 걸친 운동은 시작일로 |
| 8 | **로그 위생** | Vercel 로그에 본문 전문 금지 — 건수·출처·결과 요약만 |

### 1.5 기존 시스템 연결 (여기서 틀리면 감사가 무의미해진다)

- 저장된 운동은 **기존 수동 입력 운동과 동일한 경로**로 유효목표·판정·통계에 반영되어야 한다. 목표 계산·판정을 이 기능이 재계산하는 코드 사본은 금지 — 기존 단일 출처 함수 호출만
- 휴식 선언일에 유산소 ≥300kcal이 유입되면 **기존 자동 복귀 로직이 그대로 발동**해야 한다 (신규 복귀 로직을 만들지 말 것). 검산 완료: 복귀 시 목표 ≥1,686 > 프리셋 1,675라 판정상 무해
- 가져온 기록은 UI에서 출처 배지(예: ⌚)로 구분하고, **수정·삭제 가능**해야 한다 — insert-only 덕분에 수정은 재전송에도 보존된다

### 1.6 최소 UI

- 일일 화면: 가져온 운동에 배지 표시
- (선택 제안) 설정에 "자동 가져오기" 카드: 컷오버 날짜, 최근 수신 5건(시각·건수·결과) — 구현 여부는 3안 비교에서 규모와 함께 제시

## 2. Phase 1 — 구현안 3가지 제안 (필수)

코드를 파악한 뒤 **서로 의미 있게 다른** 3안을 제안하라. 최소 차별화 축:

- **저장 구조**: 기존 운동 컬렉션에 필드 추가(importKey, source) vs 별도 imports 컬렉션 + 참조 vs 기타
- **원자성 방식**: 문서 ID = dedup 해시(create-only) vs 트랜잭션 조회-후-쓰기 vs 별도 dedup 인덱스
- **관측성**: 응답만 vs 수신 로그 컬렉션 vs 설정 화면 카드까지

비교표 필수 항목: 변경 파일 수/규모 · race 안전성 · 기존 통계/감사 결과와의 정합성 · HAE 폴백(다른 브릿지로 갈아탈 때) 파서 추가 용이성 · 롤백 용이성. 추천 1개와 이유 명시 후 **내 승인 대기.**

## 3. Phase 3 — 검증: 계약 테스트 10종 (골든셋 등록)

| # | 입력 | 기대 |
|---|---|---|
| 1 | 정상 유산소 2건 | accepted 2, 유효목표 반영 확인 |
| 2 | 1번과 동일 페이로드 재전송 | ignored 2, 데이터 불변 |
| 3 | "기능성 근력 훈련" 1건 | filtered 1, 저장 0 |
| 4 | 한국어("실외 달리기")·영어("Outdoor Run") 혼합 | 둘 다 매핑되어 accepted |
| 5 | 컷오버 이전 날짜 운동 | rejected |
| 6 | kcal 4000 (kJ 오염 시뮬레이션) | rejected + message에 사유 |
| 7 | 날짜 "2026년 8월 6일 오후 7시" (로케일 형식) | 400 + "ISO 8601 필요" |
| 8 | 토큰 불일치 / 토큰 미설정 | 401 / 503 |
| 9 | 가져온 기록을 kcal 수정 → 동일 페이로드 재전송 | 수정값 보존 (insert-only 증명) |
| 10 | 휴식 선언일 + 350kcal 유산소 유입 | 기존 자동 복귀 발동, 목표 1,711로 상승, 판정 정상 |
| +α | 동시 2요청 (같은 운동) race 테스트 | 저장 정확히 1건 |

추가로: 기존 골든셋 전체 회귀 통과(과거 데이터·휴식일 프리셋 케이스 불변), 훅(PostToolUse·Stop·SessionStart)·CI 녹색, curl로 실전 시뮬레이션 1회(프리뷰 URL 대상) 기록 첨부.

## 4. Phase 5 — 단축어 조립 가이드 (산출물, docs/shortcut-recipe.md)

내가 폰에서 그대로 따라 만들 수 있는 단계별 문서. 반드시 포함:

1. **자동화 A (주력)**: 트리거 "Apple Watch 운동 — 종료 시" → '실행 전에 묻기' 끄기 → [15초 대기] → 건강 샘플 찾기(유형: 운동, 오늘, 최신순) → 반복: 유형·시작·종료·시간(분)·활성에너지 추출 → **날짜 포맷 지정: ISO 8601** → kcal **정수 반올림** → 사전(Dictionary)으로 JSON 조립(텍스트 템플릿 금지 — 이스케이프 안전) → URL 콘텐츠 가져오기: POST, 헤더 X-Import-Token, JSON 본문 → 응답의 message를 알림 표시
2. **자동화 B (백업)**: 트리거 "매일 21:30" (폰을 보통 쓰는 시간) → 같은 단축어 실행
3. **원탭 버튼**: 같은 단축어를 홈 화면 아이콘으로 (3차 보험)
4. 스키마 정의는 서버 코드와 이 문서가 **한 곳의 정의를 공유**하도록 관리 (어긋나면 계약 테스트 7이 잡게)
5. 실제 배포 URL·헤더명·필드명을 Phase 4 머지 후 실값으로 치환
