# Body Plan — 자동 유입 3경로 도입 후 시스템 구조 감사 (신규 세션용)

> **성격**: 신규 기능 개발이 아니라 **구조 감사(architecture audit)**다.
> 최근 2주에 ①워치 운동 자동 수신 ②인바디 체성분 HAE 수신 ③**인바디 클라우드 직수신**
> ④적응형 TDEE가 연달아 들어갔다. 각각은 자기 테스트를 통과했지만,
> **넷이 동시에 존재할 때 시스템 전체가 안전한지는 아직 검증되지 않았다.**
> 그것을 검증하는 것이 이 작업이다. 감사 대상은 기능이 아니라 **경계와 교차점**이다.

## 0. 무엇이 바뀌었나 (감사 배경)

이 앱은 원래 **모든 데이터가 사용자 손으로만 들어오는 동기 시스템**이었다. 지금은:

- 외부에서 **비동기로** 데이터가 들어온다 (운동·체성분)
- 그중 하나는 **제3자 비공식 API**(lookinbody.com)에 계정 크리덴셜로 로그인해 당겨온다
- 자동 유입분이 **초안이 아니라 확정 레코드(auto:true)로 bodylog에 직접 착지**한다
- 체중이 **adaptiveTDEE → 유효목표 보정**으로 전파된다 (체성분 오류가 칼로리 목표까지 간다)

즉 데이터 신뢰 경계·장애 전파 경로·보안 표면이 전부 바뀌었다. 개별 기능 테스트는 이 변화를 보지 못한다.

## 진행 방식 (순서 엄수)

- **Phase 0** — 필독 + 구조 인벤토리 → 보고
- **Phase 1** — 감사 축 A~R 전수 조사 → 리스크 레지스터 초안
- **Phase 2** — 시나리오 스트레스 테스트 (재현 가능한 것은 테스트 코드로)
- **Phase 3** — 심각도 판정(P0~P3) + 처방 → **여기서 멈추고 승인 대기**
- **Phase 4** — 승인된 P0/P1만 수정 (P2/P3는 백로그 문서화)
- **Phase 5** — 4중 검증 → PR + 프리뷰 → 승인 → 머지 + 보고서

**Phase 3 승인 전 코드 수정 금지.** 감사 중 발견을 조용히 고치면 무엇이 문제였는지 기록이 사라진다.

### Phase 0 필독

`api/_lib/inbody-cloud.js` · `api/_lib/body-import-rules.js` · `api/_lib/body-inbox-store.js` · `api/_lib/import-rules.js` · `api/body-import.js` · `api/health-import.js` · `api/import-inbox.js`(클라우드 pull 포함) · `api/export-view.js` · `api/cron-reminders.js` · `api/push-sync.js` · `src/bodyDraft.js` · `src/importMerge.js` · `src/adaptiveTDEE.js` · `src/syncQueue.js` · `src/bodyMetrics.js` · `src/healthEvents.js` · `src/backup.js` · `src/analysisExport.js` · `src/store.js` · `firestore.rules` · `vercel.json` · `docs/ARCHITECTURE.md` · `docs/hae-setup.md` · `docs/inbody-setup.md` · 최근 2주 커밋 로그

**Phase 0 산출물 — 구조 인벤토리**
1. 데이터 유입 경로 **전부** (수동·운동 HAE·체성분 HAE·인바디 클라우드·기타)와 각 경로의 트리거·인증·빈도
2. 각 경로가 최종적으로 쓰는 **저장소와 문서**(KV 키 / localStorage / Firestore 컬렉션)
3. 그 데이터를 읽는 **소비처 전부** (탭·통계·MA7·인사이트·adaptiveTDEE·유효목표·판정·공유 링크·크론 알림·AI 분석·백업)
4. **전파 그래프**: 자동 유입 1건이 바꿀 수 있는 것을 끝까지 따라간 경로도 (예: 체중 → adaptiveTDEE → 유효목표 → 판정 → 달성률 → 인사이트)

## 1. 감사 축 A~R

각 축마다 **현재 동작 / 위험 시나리오 / 코드 근거(파일:라인) / 판정**을 남겨라. 확인 못 한 것은 "미확인"으로 정직히 표기.

### 신규 위험 (이번에 새로 생긴 것 — 우선 조사)

| 축 | 조사 질문 |
|---|---|
| **A. 제3자 비공식 API 의존** | `inbody-cloud.js`는 인바디 앱 트래픽을 모사한다(하드코딩된 AppVersion·기기명·UA·엔드포인트 경로). 인바디가 프로토콜·앱 버전 정책을 바꾸면 어떻게 되나 — **조용히 실패하나, 사용자가 알아채나**? 실패가 지속될 때의 UX·데이터 공백은? 이 의존이 문서화돼 있나(ARCHITECTURE.md에 "비공식 경로·언제든 깨질 수 있음"이 명시됐나)? HAE 지표 경로가 **살아있는 폴백**으로 유지되나, 아니면 사실상 죽었나 |
| **B. 크리덴셜 보안·blast radius** | 인바디 계정 ID/PW가 Vercel env 평문이다. ①이 값이 로그·에러 응답·`credShape`·수신 로그에 어떤 형태로도 새는 경로가 있나 ②서버리스 함수 외에 이 env를 읽는 코드가 있나 ③토큰(JWT)은 어디에 남나(메모리/KV?) ④이 계정이 탈취되면 무엇까지 열리나(인바디 전체 측정 이력) — 이 리스크가 문서에 기록돼 있나 |
| **C. 계정 잠금 방어의 실효성** | 3-strike 잠금에 대응해 스로틀(30분)·실패 상한(3)·인증 봉인(24h)이 있다. ①스로틀 선점이 `SET`인가 `SET NX`인가 — **동시 요청 2건이 둘 다 통과해 로그인을 두 번 시도할 수 있나**(서버리스 병렬·멀티기기·연타) ②봉인 키가 실패해도(kv 오류 try/catch 무시) 재시도가 계속되나 ③"지금 확인" 버튼의 실제 호출 상한 ④실패 카운터·봉인 키가 유실되면(KV 만료·장애) 방어가 무력화되나 |
| **D. 앱 시작 경로의 외부 네트워크** | 클라우드 pull이 `import-inbox` **pull 액션 안에서 동기적으로** 돈다(maxDuration 30). ①인바디가 느리거나 죽었을 때 앱 시작 동기화가 지연·실패하나 ②그 실패가 **운동 사서함 병합까지 막나**(격리 확인) ③30초 초과 시 사서함 pull 자체가 유실되나 ④오프라인·모바일 회선에서의 체감 |
| **E. 자동 확정(auto:true) 레코드** | 이제 muscle·score까지 자동 확정돼 bodylog에 직접 들어간다. ①"muscle 미입력이 통계를 0으로 오염" 불변 조건이 여전히 성립하나(초안/확정 분리) ②**auto 확정 레코드가 통계·MA7·adaptiveTDEE·공유 링크에 수동 레코드와 구분 없이 섞이나** ③사용자가 편집하면 잠금이 걸리는데, 편집 후 더 정확한 재측정이 와도 영영 반영 안 되는 것이 의도인가 ④auto/manual 구분이 **저장·백업·공유 링크·다음 시즌 분석까지 살아남나** |
| **F. 측정 규칙 변경의 파급 (B1 완화)** | 아침 창(00~12시)이 24시로 완화돼 "하루 마지막 측정이 이긴다"가 됐다. ①이 변경이 **시즌 1 데이터(아침 공복 1회 고정)와 다른 규칙**임이 어딘가 기록돼 있나 ②저녁 비공복 측정이 그날 값이 되면 MA7·adaptiveTDEE·목표 보정이 어떻게 흔들리나(정량 추정) ③분석 계약(analysisExport)이 이 규칙 변화를 전달하나 ④되돌림(MORNING_END_HOUR=12) 시 과거 데이터 재해석이 필요한가 |
| **G. adaptiveTDEE 결합** | 체성분 자동 유입 → 추세체중 → TDEE 역산 → 유효목표 보정(±300 클램프). ①이상 체중 1건이 목표를 얼마나 흔드나(클램프가 충분한가) ②소급 유입(과거 날짜 체중이 나중에 도착)이 **이미 판정된 과거 날의 목표를 바꾸나** ③보정치가 어딘가 캐시·저장되나, 매번 재계산되나 ④입력 데이터가 부족·결측일 때의 동작 ⑤이 결합이 문서화돼 있나 |
| **H. 이중 유입 중복 (HAE 지표 ↔ 클라우드)** | 같은 측정이 두 경로로 들어올 수 있다. HAE는 애플 건강의 기록 시각, 클라우드는 인바디 DATETIMES — **sampleTs가 다르면 사서함 키가 달라 둘 다 accepted 된다.** ①이때 병합 결과가 어떻게 되나(더 최신이 이김 → HAE 샘플이 나중이면 muscle 없는 부분 갱신이 발생하나) ②값 불일치(건강 앱 반올림 vs 클라우드 원본)가 생기나 ③두 경로 동시 활성이 **의도된 구성인가**, 아니면 문서상 하나만 써야 하나 — 코드가 그것을 강제하나 |

### 기존 축 (자동 유입 도입으로 성격이 바뀐 것)

| 축 | 조사 질문 |
|---|---|
| **I. 사서함 원자성·부분 실패** | 운동·체성분 항목이 섞인 pull에서 일부만 병합 성공하면 ack(HDEL)는? 실패분 유실/재시도? 병합 중 크래시·네트워크 단절 시 최종 상태는? 병합은 멱등인가 |
| **J. 멀티 기기·동시성** | 두 기기 동시 실행 시 사서함 pull·ack 경합, 클라우드 pull 중복, `syncQueue`의 재동기화와 초안 스윕이 만드는 **유령 부활**(주석에 이미 언급된 사고) 재발 가능성 |
| **K. 지속성·수명** | `import:seen:*`는 TTL 없음(영구) — 무한 증가의 비용·한도 영향은? 사서함·throttle·failKey·authblock 키의 만료 정책과, **만료 시 방어 무력화 또는 중복 재유입** 여부. 앱 미개봉 2주 시나리오 |
| **L. 시간·날짜 귀속** | 운동(시작 시각)·체성분(측정 시각)·크론(KST 고정)·클라우드(로컬 벽시계 + 고정 오프셋 env)가 각각 다른 시간 기준을 쓴다. 같은 유틸을 공유하나 드리프트가 있나. 자정 경계·해외 체류(10월 오사카·11월 오키나와 예정)·기기 시각 오차 |
| **M. 소급 변경 파급** | 늦게 도착한 운동/체성분이 과거 날짜의 목표·판정·휴식일 자동 복귀를 바꾼다. **파생값(주간 성적표·달성률·인사이트·스트릭·MA7·TDEE 보정)을 저장·캐시하는 코드가 하나라도 있으면 전부 찾아라.** 있으면 갱신되나 화석이 남나 |
| **N. 통계·분석 정합성** | ①초안이 통계에 새는 경로 0인지 재확인 ②근력이 단일 종목으로 들어오며 **부위 구성비 인사이트가 거짓을 말하나** ③자동 유입 전후로 의미가 달라진 지표 목록 ④`analysisExport`가 provenance(auto/manual·경로)와 규칙 변경을 전달하나 — 다음 시즌 분석이 조용히 틀리지 않으려면 필수 |
| **O. 이중 계상 방어** | 유산소를 수동으로도 적으면? 방어가 **문서에만 있나 코드에도 있나**. 체성분 수동/자동 충돌은 잠금으로 충분한가 |
| **P. 보안·권한** | 운동·체성분이 `IMPORT_TOKEN` 공용 — 한쪽 유출 시 blast radius. rate limit 실효성. `firestore.rules`가 새 필드/키를 덮나. **클라이언트가 auto:true 레코드를 위조해 쓸 수 있나.** 로그 위생 |
| **Q. 침묵 실패·관측성** | 자동화의 최대 위험은 고장이 조용하다는 것이다. 단축어가 iOS 업데이트로 깨지거나 인바디가 프로토콜을 바꾸면 **아무 일도 안 일어난 것처럼 보인다.** ①현재 "N일간 유입 없음"을 감지하는 장치가 있나 ②수신 로그 20건·설정 카드가 그 역할을 충분히 하나 ③없다면 가장 싼 구현(기존 크론 재사용 등) |
| **R. 롤백·수습** | env 스위치(IMPORT_BODY_CUTOVER_DATE / INBODY_LOGIN_*)가 **실제로 독립적인지 코드로 확인**. 잘못된 데이터 대량 유입 시 ①즉시 차단 ②유입분만 골라 일괄 삭제(출처 필드로 식별되나) ③삭제 후 통계·TDEE 보정 정상 복구 |

**S. 구조 부채**: 운동/체성분 두 파서·두 병합 로직 사이 복붙 드리프트, 규칙 단일 출처 준수 여부, **유입→병합→통계→목표→공유 링크 전 구간 관통 통합 테스트의 존재 여부**(34개 테스트 파일이 단위 위주인지).
